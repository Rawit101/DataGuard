# Full system verification

Verified 12 October 2026 on macOS with Python 3.12, Node 22, the built frontend at `http://127.0.0.1:8000`, and the real FastAPI worker. All new projects, uploads, jobs, and outputs were placed under `work/full-system-workspace` or temporary test workspaces. Existing user projects and the default `.dataguard` directory were not changed. The server remained bound to `127.0.0.1`.

`PASS` means the observed result was checked against a stated expectation. `UNVERIFIED` means the cited check did not complete; it does not imply a product defect. There are no known remaining functional failures from the completed checks.

## Independently calculated expectations

The non-demo `harbor_orders.csv` fixture contains nine valid records plus one malformed six-field record. `amount=bad` and `ordered_on=not-a-date` stay in the accepted raw-value table with separate parse issues, producing three total import issues. The duplicate `H2` rows have source IDs 2 and 3; `H5` has the unmatched zone `X`; `H6` has missing customer and amount. The ten-step clean and join pipeline must have row counts `9, 8, 7, 6, 5, 5, 5, 5, 3, 3`, then output `เหนือ: 3 orders/350`, `ใต้: 1/150`, `ไม่ทราบ: 1/400`. A changed input file increases the northern total to 370. Duplicate `N` lookup keys multiply one join group and produce four final groups. These expectations were calculated from the fixture records, then asserted independently from downloads and API responses.

## Checks, scale and limits

- `.venv/bin/pytest -q backend/tests` → **47 passed**, one installed Starlette/AnyIO deprecation warning.
- `cd frontend && npm run test` → **2 passed**. `npm run lint` → **passed**. `npm run build` → **passed**, including TypeScript compilation and production bundle.
- `cd frontend && DATAGUARD_WORKSPACE=/absolute/separate/workspace npm run e2e` → **UNVERIFIED**: two tests could not start because sandboxed macOS refused Chromium Mach port registration (`Permission denied (1100)`). The in-app browser completed the real UI workflow listed above. On a machine that permits Chromium, stop the app on port 8000, run `npx playwright install chromium`, then rerun `npm run e2e` with an empty workspace path.
- Fresh synthetic Parquet load: **100,000 rows**, source **957,381 bytes**; final 1,000-row pipeline Parquet **20,195 bytes**. Last run: inspect 0.009 s, commit 0.012 s, deep page 0.021 s, exact profile 0.014 s, 100-group SQL 0.007 s, 1,000-row preview 0.008 s, queued-to-completed pipeline 0.213 s. The browser showed page 1 and page 2 of 2,000 at its 50-row page size. API rejected page size 101 and returned only 50 rows from a 1,000-row pipeline preview. These are local measurements, not a general throughput claim.
- The load-driver process reported a peak resident set of **77,627,392 bytes** (about 74 MiB), 0.120 s user CPU and 0.030 s system CPU. This excludes the separate API and worker processes; their peak RSS was unavailable in this sandbox. A separate `/usr/bin/time -l` attempt could not retrieve kernel counters because `sysctl kern.clockrate` was denied, although the workload itself completed.
- The in-app browser download event for the Blob-based **Download runnable SQL** action did not surface before its 10-second wait. The server logged `POST /api/pipelines/script` 200, and a direct test verified its SQL content. A later read-only browser observation was not executed because automatic approval review returned **429 Too Many Requests**. This was a review-service limit, not a judgment that the action was unsafe. The remaining individual UI controls listed as unverified above need another browser session or the standalone Playwright suite on a host where Chromium launches.
- The SQL-script Blob URL now remains valid for 30 seconds after clicking its attached download link. This browser compatibility change passed type checking, linting and build; a native download-complete event could not be observed in this environment.
- Browser behavior was checked at 375, 768 and 1280 px. The 375 px document measured 376 px wide; this one-pixel overflow did not hide the mobile navigation or form controls. Windows and Linux launch behavior were not exercised on this macOS host.

## Launch and reproduce

From the DataGuard project root, install dependencies as in `README.md`, then run:

```sh
DATAGUARD_WORKSPACE=/absolute/path/to/an/empty/audit-workspace .venv/bin/python scripts/dev.py
```

Open `http://127.0.0.1:8000`. Create a project; import `backend/tests/fixtures/harbor_orders.csv` and `zone_lookup.csv`, declaring `amount` DOUBLE and `ordered_on` DATE. Confirm 9 accepted rows and 3 issues; inspect Preview, Schema, Profile and Import issues. In SQL Workspace run `SELECT zone_code, count(*) AS n FROM harbor_orders GROUP BY zone_code ORDER BY zone_code` and expect `N=5,S=3,X=1`. Create a warning parse-valid DOUBLE rule for `amount` and expect one failure (`H3`). In Pipeline Builder trim customer/zone, drop missing amount, cast amount and date with `drop`, deduplicate `order_id` keeping first by `__source_row_id`, left join the zone lookup, fill unmatched zone name, calculate a tax value, group by zone name with count and amount sum, and sort. Preview should show 350/150/400; save and run, then inspect 10 step counts and download the Parquet output in Runs & Exports. Export the full SQL result as CSV with BOM. Stop and restart with the same workspace path, then reopen the project and its artifacts. For changed-input behavior, import `harbor_orders_changed.csv` into a separate project and expect the northern total to become 370.

To rerun the deterministic checks, use the commands above plus `scripts/audit/full_system_load.py`, `scripts/audit/full_system_cancel.py`, and `scripts/audit/full_system_artifacts.py` from the repository root. The artifact and cancellation scripts require the saved local audit workspace, which is excluded from Git. The cancellation script's project IDs refer to that workspace; create new IDs if running against a different workspace.
